# VoiceFlow — Realtime Audio Pipeline: Design Notes

This document describes two real, specific engineering choices in
VoiceFlow's realtime voice-agent bridge (`WS /realtime`, Gemini Multimodal
Live path) — not a research paper, and not a source of benchmark numbers.
For actual measured results, see the `eval/` benchmark suite and its
generated `.md` reports (`WER_BENCHMARK.md`, `MULTI_PROVIDER_BENCHMARK.md`,
`REALTIME_BENCHMARK.md`, `SCENARIO_BENCHMARK.md`, `ACTION_ITEM_BENCHMARK.md`)
— each one states plainly what it does and doesn't measure, and is
reproducible by running the matching script yourself.

## 1. Why downsample at all

Gemini Multimodal Live's input side expects 16kHz 16-bit mono PCM; a
browser's `MediaRecorder`/Web Audio pipeline more commonly captures at
24kHz. Rather than push that mismatch onto every client, `api.py`'s
`ws_realtime` handler downsamples server-side with the standard-library
`audioop.ratecv` call before forwarding audio to the Gemini session.

The ratio is a straightforward 3:2 linear decimation — 3 input samples map
to 2 output samples:

$$y[n] = x\left[\left\lfloor \frac{3n}{2} \right\rfloor\right]$$

which reduces the raw payload bitrate by exactly 33.3% (384 kbps → 256 kbps
for 16-bit mono PCM) while staying well above the ~4kHz bandwidth that
matters for intelligible speech. This is standard, well-understood signal
processing — not a novel technique — applied at the one point in the
pipeline (client → server → provider) where it actually needs to happen.

**Real measured latency** for this specific operation (the actual
`audioop.ratecv` call, not a simulated stand-in) is in
`eval/run_benchmarks.py` / its generated `eval/benchmark_results.json` —
reproduce with `python3 eval/run_benchmarks.py`. On typical hardware it
runs in tens of microseconds per 20ms chunk, i.e. not a meaningful
contributor to overall latency next to real network round-trip time.

## 2. Why gate input during tool calls

When the model is mid-tool-call (`is_tool_active`), `ws_realtime` stops
forwarding new microphone frames to the provider until the tool call
resolves. Without this, speaker output audio bleeding back into an open
microphone during a tool call can be picked up as new input, which reads
to the model as an interruption of its own tool-call turn. The fix in
`api.py` is a single conditional (`if is_tool_active: continue` before any
frame is forwarded) — deliberately simple, since correctness here follows
directly from the code structure rather than needing runtime measurement.
It's exercised by the realtime tests in `tests/test_e2e.py`.

## 3. Where this sits in 2026

Bidirectional, low-latency multimodal voice APIs (Gemini Multimodal Live,
OpenAI's Realtime API) went from preview/beta to production-grade,
widely-integrated infrastructure over 2025–2026, and WebSocket-bridged
voice agents with client-side barge-in and tool-calling — the pattern
VoiceFlow implements here — are now a well-established architecture for
this class of application, not a novel one. VoiceFlow's contribution is a
clean, provider-agnostic implementation of that pattern (`REALTIME_PROVIDER`
switches between OpenAI and Gemini with no code fork, and external
tool-calling is bridged through a generic discovery contract rather than
hardcoded to one product) rather than a new technique in the pipeline
itself. Where VoiceFlow's own numbers matter, they live in the `eval/`
benchmark reports linked above, generated by scripts that state exactly
what they measure and don't pad results with anything unmeasured.
